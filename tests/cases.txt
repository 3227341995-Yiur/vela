# tests/cases.txt — the corpus, one case per line:
#
#   <mode>  <name>  <path>
#
# mode      what must be true
# ------------------------------------------------------------------------------
# run       built by the compiler under test and executed, and *also*
#           interpreted: both must print tests/golden/<name>.out exactly.  The
#           compiler's `build` is the LLVM back end now — the module is built in
#           process through libLLVM and linked by `lld-link`, with no C compiler
#           started — so this is the row that says "the default path compiles
#           this program and its answer is the interpreter's"
# run-c     the same case, with `build-c`: the C back end, which emits C and
#           hands it to the host's C compiler.  Every row that says `run-c` is a
#           program the LLVM back end refuses **by design** and is listed in
#           tests\llvm-refusals.txt; the comment above each row says which
#           construct it is.  There is no fallback inside `build`, so a program
#           the LLVM back end cannot compile has to be named here, one row at a
#           time, where a reader can see it
# refuse    `check` must fail with the first bytes of stderr equal to
#           tests/golden/<name>.err, and must write nothing to stdout
# panic     it must compile, and the program must then stop at run time with
#           tests/golden/<name>.err as the head of stderr; the interpreter must
#           stop too.  `panic-c` is the same case built by the C back end
# ok        `check` must accept it and report ok
# dumps     the digests of `lex`, `parse` and `emit-c` must all match
#           tests/golden/digests.txt — three checks, three digests, so a change
#           in the back end cannot hide behind an unchanged parser
# lex       one of those three on its own, for a file that cannot be parsed
# fixpoint  the compiler must build itself through its own driver (the LLVM path,
#           the default), and the compiler it built must emit the C the compiler
#           emits — byte for byte, and the same C as the checked-in seed
#
# Every refusal here is a program Python or C++ would accept and misbehave on,
# and every `ok` is a program a conservative compiler would be wrong to refuse.
# The two halves are the point: a compiler that refuses one program too many is
# as broken as one that accepts one too few.

# --------------------------------------- the aliasing rule of `parallel for`
#
# An array the body **writes** may be read inside that loop only at the write's own
# index expression.  It is the language-level form of what Rust's `par_iter_mut`
# enforces by construction — an iteration is handed its own element and cannot
# reach another iteration's — and it is why `a[i] = a[i - 1] + 1` cannot be written
# here at all: before the rule existed that program compiled to
# `#pragma omp parallel for` and printed **nine different wrong values in twenty
# runs** (3, 7, 11, 15, 19, 27, 31, 51, 55) while the interpreter printed 63.
#
# Five cases, because a rule is only worth having if both directions are held: one
# program that must be refused, and four that must keep compiling — including the
# two shapes the benchmarks and ordinary accumulation depend on.
#
# These are NEW cases, written together with the rule, and their goldens have not
# been recorded yet.  `tools\refreeze.ps1` records them while keeping every
# existing `.out`/`.err` byte for byte (a golden is an expectation and must not be
# replaced by the compiler's own output).
#
# All four carry a `parallel for`, so all four are `run-c`: the LLVM back end
# refuses them by design (`tests\llvm-refusals.txt`), and the C back end is what
# compiles them.  That is four of the seven.

# ------------------------------------------- enums with payloads, and `match`
#
# The twelve programs ENUMS_PLAN.md's acceptance table names.  They were written
# for `tests/accept/` (which pins what the compiler says *before* a feature lands)
# and they move here, the way that directory's own README says they would, on the
# day the feature landed: each one moves into tests\cases.txt with a golden, and
# BASELINE.txt is re-recorded without them.
#
# Four of them are `run` -- both paths, byte for byte -- and the rest are `refuse`,
# because a feature is only implemented if the programs it must reject are
# rejected *for the reason the table gives*, with the missing variant named in the
# diagnostic.
#
# `enum_in_array` is `ok` rather than `run`, and that is a measured limit and not a
# preference: the C back end refuses `Array[E, N]` by name -- an array of
# aggregates, which it does not lower for structs either -- so there is no compiled
# program for a `run` row to compare against.  The interpreter runs it, and its
# output was checked by hand against the bytes in that program's header.
#
# `enum_two_enums` and `enum_else_arm` are new here.  The first is the regression
# case for a bug this corpus could not have caught: every program in tests/accept
# declares exactly one enum, so an enum table whose variant lists all began at
# record 0 looked correct, and with two enums the exhaustiveness rule judged the
# second one against the first one's variants.  The second is the `else` arm that
# runs -- the table only ever had the refusal for an `else` in the wrong place.

# These five are `run-c`, and that is the merge of two facts rather than a preference.
# `build` is the LLVM path now (see the mode table at the top of this file) and the LLVM
# back end refuses an enum value **by name** -- "an enum value is a tagged union, and this
# back end has no lowering for one" -- with the five enum rows of `tests\llvm-refusals.txt`
# as the other side of that ledger.  The C back end lowers them (a tagged union, a
# designated-initialiser constructor, a `switch` with no `default`), so the compiled answer
