状态：**尚未开始，而它的第一步是一个现在还不存在的前置条件。** 这是流 1 的第 3 项（`ROADMAP.md` 中的"由证明驱动的检查消除——*真正的性能杠杆*"）。它不需要 LLVM。它确实需要**一项新的分析**，而这件事是一名 agent 去读 `parts/check.vel`、而不是去实现本文件最初描述的方案之后才确定下来的——本段更早的一版草稿声称"检查器已经证明了这些事实"，那是**假的**：

  * 区间机制——`iv`、`lb`、`Par` 游标——被声明为 **`ck_parallel` 的局部变量**，并在 `ck_pcol`/`ck_pwrite` 之间传递。其他任何函数都没有区间环境，所以其他任何函数都算不出范围；
  * `ck_index`（`check.vel:897-936`）**只判定常量下标**：它要一个简单名字的基准和一个已知长度，而每一个非常量下标都返回"未定"；
  * `ck_match_linear`（`1841-1862`）证明的是**单射性，不是范围**，而且从不查阅数组的长度；
  * `ck_stmt` 的普通循环调用 `ck_block`，所以在一个**普通**循环里——而 `bench/matmul.vel` 的内层循环恰恰就是普通循环——检查器根本不计算任何区间。

`SPEC.md` §6.1 中关于循环变量跟踪与条件收窄的那两行老实地标着"已设计，未实现"，而它们就是缺失的前置条件。因此下面的工作把分析排在第一位；它最终写下的那两个位是接口，而接口恰恰是永远不必再改的那部分。

## 今天真实成立的事，实测

`bench/matmul.vel`——一个朴素的 512×512 三重循环——编译出的 C 里含有

    6 vela_bounds_check      10 vela_add_range      6 vela_mul_range      1 #pragma omp parallel for

而它们就在最内层循环里。`bench/RESULTS.md` 记录了这个代价：Vela 的并行构建比用 `restrict` 和 OpenMP 编译的 C++ 孪生子**慢 3.1×**（0.0680 s 对 0.0221 s——2026-09-22 实测；这一段过去写的是"慢约 17%"，那是一个取自 2026-09-19 那处 emitter 修复之前读到的值，它错得离谱），而 Vela 的*串行*构建比它的串行 C++ 孪生子慢 2.4×（0.5433 s 对 0.2241 s），并且它自己对*串行*胜利的解释（"语言规则带来的 `restrict` 加上已被证明消除的边界检查"）被实测推翻并更正了——`restrict` 从来没被生成过，而且**没有任何检查曾被证明消除**。

所以这门语言为那些它已经展示为不必要的检查付出了代价，而 README 顶部那句"比 C++ 更快"的断言，恰好就在解决问题之后的另一侧。

同时那些诚实的话已经到位：`SPEC.md` §6.1 和 `DESIGN.md` §3 都说，用证明删除一次检查**尚未实现**。这项工作要做的是让那些话从描述一个缺口变成描述一个特性。

## 这个决定记在哪里：节点的 `flags` 字里的两个空闲位

这项工作首先要回答的问题是：每个位置的决定可以住在哪里。这个问题由 `selfhost/AST.md` §1.1 回答，而不是由偏好决定。读一下：

- 一个节点是**十个字**，`nd[i*10 + k]`，而且*十个字全都各有其主*——0 是 `kind`，1–4 是负载，5 是 `line`，6 是 `flags`，7 是 `nx`，8 是 `e`，9 是 `f`；
- 因此，"把它存进节点里某个空闲的字"和"把一个平行数组穿过每一个接收 `nd` 的函数"都不可接受。平行数组是两者中更糟的那个：它改变了 `parser.vel`、`resolve.vel`、`check.vel`、`eval.vel` 和 `emit.vel` 中每一个函数的签名，而这么做的理由是一个只有其中两个文件会用到的特性；
- 字 6 即 `flags`，目前用到**第 1 位**（`mut`）、**第 2 位**（`declaration`）、**第 4 位**（`pure`），以及 `for` 的第 1 位表示 `parallel`。第 3、5、6、7 位及以上都是空的，这个字是有符号 64 位整数，而解析器在分配时就已经把它初始化了。

**所以决定就是字 6 的两个位**，其它什么都不动：

| 位 | 名字 | 含义 | 由谁写入 | 由谁读取 |
|---|---|---|---|---|
| 8 | `NF_NO_BOUNDS` | **指下标节点的字 6**：这个下标位置的范围已被证明，所以不再生成 `vela_bounds_check` | 区间遍历，一旦它运行在 `parallel for` 之外 | `emit.vel`，在下标处 |
| 16 | `NF_NO_OVERFLOW` | **指运算符节点的字 6**：这个算术位置的运算结果区间已被证明落在 `int64_t` 内，所以不再生成 `vela_add_range`/`sub`/`mul` | 同一次遍历 | `emit.vel`，在运算符处 |

两个位都是**按节点种类**生效的，因为字 6 在不同种类上含义不同——而且**第 8 位在 `def` 节点上已经被占了**：`parser.vel` 对没有函数体的 `extern c` 声明写入 `xflag = 8`（`extern c pure` 写 `12` = 8|4），解析器与 emitter 就是靠它认出这种声明的。在这个特性要标记的节点（种类 31 下标、种类 27 运算符）上，第 8 位和第 16 位是空闲的，这正是选它们的理由；但计划必须说清楚它指的是*谁的*字 6，否则下一个读者会把它们当成全局位。

用两个位而不是一个位，是因为这两条证明是不同的事实：一个下标可以被证明在范围内，而下标*表达式*本身仍然需要自己的溢出检查，把两者合并会消除掉一项分析从未证明过的检查。

`AST.md` §1.1 与 §9 必须同一次改动一起更新——它的开头就写着 §9 是"AST 不记录什么"的清单，而它正是读者信任的那份关于字布局的文档。一个没人记录过的位，就是下一个读者会拿去复用的位。

是**按位置**，不是按标志位。`SPEC.md` 明确说检查只由证明删除，绝不由标志或注解删除，这话是对的：一个把检查关掉的编译标志，就是这个项目已经删过一次的 `--fast-int` 谎言。这些位由分析一次一个位置地设置，除此之外任何地方都不清除。

这次改动的形态仍然是可用的选项里最小的那个：检查器设置位，emitter 读取位，其它什么都不动。下面的第 1 项设置位并让 emitter **忽略**它们，那是一个完全没有行为变化的改动。

## 健全性规则

1. **只在现有区间分析在*该点*证明了事实的地方消除**，包括它的失效规则：循环内任何地方被赋过值的对象，其事实在循环入口被丢弃，所以证明不可能在回边上过期。仅仅*在这条路径上为真*的证明不够。
2. **一次一个位置。** 循环里的 `a[i]`，如果循环的迭代范围证明了 `0 <= i < len(a)`，就丢掉它的边界检查；同一个 `a[i]` 若所在循环的边界没有被证明，就保留检查。任何地方都没有"这个函数已检查/未检查"的开关。
3. **`parallel for` 与任何其他循环一视同仁。** OpenMP 的任何东西都不改变范围证明；别名规则（已经写好）阻止的是*数据竞争*，那是另一个问题。
4. **范围超出的常量下标绝不消除**——那是一次拒绝，不是一次消除，而且它现在就能用。
5. **绝不能发生的事**：一个错误答案。一次不健全的消除是这个项目可能发布的最糟的 bug，因为它是静默的，也因为其它一切保证都建立在"检查在那里"之上。所以下面的计划把消除安排为*最后*一个打开的东西，也安排为每一步都可以被单独证伪。

## 工作顺序

要做的事情有七件，而它们之间的顺序就是本节的论证。下面的清单编号是 **1–5**：第 1、2、3 项各是一件工作，第 4 项要做两次（一次是 emitter **忽略**那两个位，一次是它听从它们），而第 5 项既是"对那次改写的改写"，又是第二个杠杆。这份清单此前读作 `1,2,3,4,4,5`，那不是一种编号。

1. **把区间遍历扩展到普通循环**——循环变量跟踪与条件收窄，用并行证明已经在用的同一套形态，由普通的语句遍历驱动，而不是由 `ck_parallel` 驱动。这就是那个前置条件，也是"比 C++ 更快"真正住着的地方：matmul 的检查全都在普通循环里，所以本文件后面任何东西都不可能在没有它的情况下移动那个数字。验收：一个按位置报告遍历所算出的区间的探针（下面的第 3 步列出了那些程序），以及**生成出的 C 不发生任何变化**——目前还没有东西消费区间。
2. **检查器写入那两个位；emitter 仍然忽略它们。** 完全没有行为变化，而且整个语料必须保持全绿，这就在任何东西依赖它之前证明了写入是无害的。只对第 1 项的遍历真正证明的位置写入：从一个并不存在的证明里设出的位，正是本文件通篇在设法避免的不健全。`AST.md` §1.1 在同一次改动里记录这两个位。
3. **证明这个证明。** 一个探针，对一组对抗性程序按位置打印"已证明"或"未证明"，再由人工核对：
   - `for i in range(0, len(a)) { a[i] = 0 }` → 已证明；
   - `while i < 10 { a[i] = 0; i += 1 }`，其中 `a: Array[int, 10]` → 已证明；
   - `while i < 100 { a[i] = 0; i += 1 }`，其中 `a: Array[int, 10]` → **未证明**
     （而且在运行期它仍然必须 panic）；
   - `a[i + k]` 里的 `k` 未被证明 → 未证明；
   - `a[i - 1]` 出现在 `for i in range(1, n)` 里 → 仅当 `n <= len(a)` 时已证明；
   - 循环内任何被赋过值的东西 → 未证明。
4. **emitter 读取这些位。** `bench/matmul.vel` 的内层循环必须编译出**零**个 `vela_bounds_check` 与**零**个 `vela_add_range` 调用，同时程序打印出完全相同的答案，并且整个语料保持全绿——差分证据的重要性就在这里，因为语料里的 `run` 用例是既编译*又*解释执行的，而解释器仍然检查一切。**解释器是这个特性的参考实现**：打开消除后，编译路径与解释路径仍然必须逐字节一致，一旦它们不一致，就是消除错了。
5. **测量，并且无论结果是什么都报告出来。** `powershell -ExecutionPolicy Bypass
   -File tools\bench.ps1 -Reps 7`，带上线程扫描，并把 `bench/RESULTS.md` 用新数字连同取数日期与编译器重新冻结。如果并行的差距没有合拢，表格就这么写，而那个断言保持未获证明。

## 第二个杠杆，以及它为什么是第二个

实测于 2026-09-19，同一份生成出的 C，所有变体都打印 1090512707：

| 变体 | 秒 |
|---|---|
| 按 emitter 今天写出来的样子 | 1.058 |
| 下标提升进一个临时变量，算术仍然带检查 | 0.550 |
| 下标不带检查，边界检查保留 | 0.177 |
| 什么都不检查 | 0.181 |
| C++ 孪生子 | 0.213 |

由此推出两件事。第一，emitter 目前把每一个下标表达式写了**两遍**，修掉这一点（另一件独立的工作，在 emitter 里）就是把 1.058 s 变成 0.550 s 的原因。第二，*在那次修复之后*，带检查的下标算术是 0.550 → 0.177，也就是**剩下那部分的约 68%**——这正是本计划存在的全部理由，也是输给 C++ 孪生子和胜过它之间的差别。边界检查是较小的一半——`bench/RESULTS.md` 那张阶梯表里的一行，价值 `0.543 − 0.514 = 0.029 s`；这句话过去引用的 `~0.04 s` 无法从那张阶梯表里推出来（见那份文件的算术说明）——所以真正划算的一半是下标算术上的 `NF_NO_OVERFLOW`，而 `NF_NO_BOUNDS` 是较小的一半。
（这一项更早的版本声称这些检查不花什么代价，因此本计划的价值低于它看起来的样子。那个结论来自一个手工改过的变体，它标着"检查保留"，实际上却提升的是*不带检查*的算术，所以标签并没有描述那次测量。上表取代了它。）

## 第 1 项必须构建什么，以及代码已经在用的那种形态

那个前置条件**不是新算法**——算法已经存在。它是一次**作用域的变更**：区间遍历必须能为普通循环运行，而并行证明必须变成它的*调用者*之一，而不是它状态的拥有者。

就 `parts/check.vel` 读到的内容：

| 部件 | 它今天住在哪里 | 第 1 项拿它怎么办 |
|---|---|---|
| `iv`、`lb`、`Par` 游标 | **`ck_parallel` 的局部变量**（约 2400-2447） | 提升进一个由普通语句遍历拥有的上下文 |
| `ck_iv_expr`、`ck_iv_push`、`ck_lb_push`、`ck_range_iv` | 只从 `ck_pcol`/`ck_pwrite` 调用 | 从 `ck_block` 的循环处理里调用它们，并像以前一样也从 `ck_parallel` 调用 |
| `ck_clamp` | 把一个已知端点保持为**真**界（±2^62） | 不变——正因为它，两端都已知的 `Iv` 才是*证明*而不是猜测 |
| `ck_match_linear`、`ck_rowmajor`、`ck_linear` | 单射性证明，另一个问题 | 不动；它们继续为自己的目的消费区间 |

这次扩展必须守住的三条规则，因为并行证明已经守住了它们，而它们正是它健全的原因：

1. **在循环内部建立的事实于循环入口被丢弃**——现有的失效规则。没有它，证明就会在回边上过期，而那是"已证明"的边界检查变成错误答案的经典方式。
2. **收窄是按分支的，不是按函数的。** `if i < len(a) { a[i] }` 只在那一个分支里证明该下标，而遍历在汇合点必须朝**最宽**的区间合并，绝不能朝最窄的合并。
3. **这一步里没有任何东西消费区间。** 生成出的 C 一个字节都不能变，所以 190 用例语料与不动点*就是*验收测试：其中任何一个发生变化，都是第 1 项的 bug，而不是它的特性。

第 1 项的验收是一个探针，按位置打印遍历算出的区间，运行在第 3 项那些对抗性程序上。那个探针需要一个可打印的地方，而形态很重要：一个在 `check` 期间触发的 dump 会把噪声放到每个用户的 stderr 上，而一个启用它的标志又会是 `SPEC.md` 拒绝的那种开关。所以它是一个**独立的驱动模式**——`vm.exe iv <file>`，在现有九个模式旁边加上的第十个模式——并作为开发者工具记录下来。探针是让"已证明"可被证伪的东西；一个没有任何东西打印区间的证明断言，就是这个项目不得不一再撤回的那种断言。

## 本文不声称什么

它并不从语言里拿掉*检查*——它拿掉的是编译器已证明为不必要的那些检查，而这正是这门语言一直说自己会做的事。它不加标志，而且绝不能加：一个放宽安全性的用户可见开关，正是把"Rust 的安全设计"变成口号的东西。它也不碰解释器——解释器永远保留每一项检查，而这正是它能成为用来检验编译器的参考实现的原因。
