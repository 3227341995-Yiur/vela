    powershell -ExecutionPolicy Bypass -File tools\bench.ps1 -Reps 7

那一条命令用树里的编译器构建测试框架、构建每一个变体、把每一个运行七次，然后打印下面的表格。它里面没有 Python，仓库里任何地方也没有：测试框架是一个 Vela 程序（`bench/run_bench.vel`），由它正在测量的那个编译器构建出来。

## 这些数字是什么

* **机器**：AMD Ryzen 7 9800X3D，8 核 / 16 逻辑处理器，~4.7 GHz，Windows，两边都用 MSVC `/O2`（`cl` 来自 VS 2022 BuildTools，并行变体用 `/openmp`）。一台机器的数字，取在一台除此之外空闲的机器上。
* **重复次数**：每个变体 7 次。*median* 是标题数字；*best* 与 *worst* 就在它旁边，好让离散度不被藏起来。
* **时钟从哪里读**：在*每个程序内部*、围绕着被计时的那个循环——不是进程的墙上时间，所以进程的启动与收尾哪一边都不偏袒。
* **每个答案都被检查**：最后一列是这个变体必须打印的值。一个又快又错的答案是失败，不是结果；只要有任何变体对不上，测试框架就以非零退出。
* **编译器**：提交 `a0b2078`+ 处的树（把每个数组下标只计算一次的 emitter），不动点 `15EAE445780BAA58…`，种子 `selfhost\build\vm.c` 754867 字节，`selfhost\build\vm.exe` 633344 字节。`.c`、`.ll` 与目标文件都进 `%TEMP%\vela-build\`；这些构建留在它们源码所在目录里的唯一文件，就是那个可执行文件。

> **来源说明，2026-09-22 补：上面点名的那个提交不可达，而这个块实际描述的是 `622c686`。**
>
> `git merge-base --is-ancestor a0b2078 HEAD` 以 1 退出，而 `git rev-list --all` 里也没有它——这台机器上没有任何 ref 能到达它。列出它的是 **reflog**，不是 `--all`：2026-09-22 实测，`git log --all --oneline` 对 `a0b2078` 匹配到**零条**，而 `git log --reflog --oneline` 会打印出 `a0b2078 Correct a wrong performance conclusion, and run the phase-2 spike`（那个提交的日期是 2026-09-19 03:48:09 +0800，它的父提交是可达的 `9299967`）。reflog 正是一个读者会把它当成历史的原因：它是一条被改写过的开发线留下来的记录，不是一个能拿来构建任何东西的提交。（这段说明更早的版本说 `git log --all` 会列出它，那是错的；这里的机制是按能复现它的那条命令写的，因为一条用做不到的命令去解释一个错误的说明，就是在新的地方犯了同一个错误。）所以上面那个标题不能像钉子那样使用：它引用的四个量，是对一个你检不出来的修订版的测量。

* **串行 matmul**：`0.543302` 对 C++ 的 `0.224054` = **慢 2.42×**——与上面那个块记录的是同一个差距，而这是在晚两个修订版的编译器上。
* **并行 matmul**：按 7 次里取最优是 **慢 3.49×**（`0.070122` 对 `0.020099`），按中位数是 **慢 2.80×**（`0.082397` 对 `0.029377`）。本文件过去引用的那个单一数字「3.1×」，是一个会因为读哪个统计量而变动四分之一的比例，所以这里两个都写下来，而不是只写一个。
* **mandelbrot 1600×1200**：`0.011805` 对 `0.011710` = **打平**，与已记录的一致。
* **sieve n = 20×10⁶**：`0.019680` 对 `0.013152` = **慢 1.50×**。

**「比 C++ 更快」在任何一行上都不成立**，而现在这是第三次独立运行给出同样的结论。代价只有一处：Vela 的内层循环保留着带检查的下标算术，而每一行都打印了它必须打印的答案，所以更快的那些变体不是靠算错才快的。用证明把那部分算术去掉，是这个项目唯一的杠杆（`selfhost/ELISION_PLAN.md`）；在它让这些数字移动之前，那个说法都不成立。

## 拿本文件与它的旧副本比较之前，先读这一节

上一张表是**被删除的，不是被编辑的**。它的 Vela 行是在两个缺陷都还活着的时候测出来的，而这两个缺陷都不微妙：

1. **溢出测试是空洞的。** `vela_sub_range` 之流把结果回绕进一个 `int64_t`，再拿它去比 `INT64_MIN..INT64_MAX`——一个没有哪个 `int64_t` 能离开的区间——所以带检查的算术根本不可能触发。一个编译后的 `x = x + one()`，当 `x = 9223372036854775807` 时打印出回绕后的值并以 0 退出，而解释器却 panic 了。已修复；语料现在覆盖了它。
2. **emitter 把每个数组下标表达式写了两次**，一次在边界检查里，一次在下标里，于是每次元素访问，带检查的下标算术都要跑两遍。2026-09-19 修复，办法是把下标只计算一次、存进一个语句作用域的临时变量；发出的编译器从 850572 → 754867 字节，matmul 串行从 1.058 s → 0.543 s。

旧表说 Vela 的串行 matmul *打败了*两个 C++ 串行构建。它没有，而对那个旧数字诚实的读法是：它是在检查根本不可能触发的状态下测出来的。把那张表留在这张旁边，正好会招来恰恰错误的结论，所以它没了，而本文件就是那些数字当年是什么的记录。

    Vela serial            0.540116   0.543324   0.546360  1090512707

    Vela parallel          0.065715   0.068042   0.076169  1090512707

Vela 串行比 C++ 串行的孪生版本**慢 2.4×**（0.5433 s 对 0.2241 s），而 Vela 并行比 OpenMP 的 C++ 孪生版本**慢 3.1×**（0.0680 s 对 0.0221 s）。两个差距都来自同一个地方，测量办法是拿同一份发出的 C，一次只去掉一样东西：

    variant                                  seconds
    as the emitter writes it                 1.058     (before the index fix)
    index computed once, checks kept         0.543     <- this compiler
    index once, bounds check also removed    0.514
    index unchecked, bounds check kept       0.177     <- the arithmetic checks are ~0.37
    nothing checked                          0.181
    the C++ twin                             0.227

> **算术说明，2026-09-22 补：这张阶梯表里有两个数字彼此不自洽，两个都被点名了。**
>
> * `0.514` 那一行过去带着一句注解"（边界检查约 0.04）"。严格按这张阶梯表本身算，边界检查是 `0.543 − 0.514 = **0.029**`，而 `0.04` 那个数从上面任何两行的相减都推不出来——它是从 2026-09-19 那批手工编辑变体里带过来的读数，所以那句"约 0.04"的注解是被去掉，而不是被猜一个补上。`0.04` 当时到底在量什么，本文档里已经无法复原，因此这里不再断言它。
> * "C++ 孪生版本 `0.227`"与本文档自己的孪生行（中位数：串行 `0.224069`、`restrict` `0.231455`）不一致，而上面每一处比较用的都是*串行*那一行。`0.227` 照原样留着，因为它是那次有日期的测量的一部分，不是派生值；读者应当拿来比较的是表格自己的数字。
> * 下面的 `约 68%` 是对这张阶梯表做的算术，它是成立的：`0.543 − 0.177 = 0.366`，而 `0.366 / 0.543 = 0.674`。
>
> 这段说明与 `bench/RESULTS.md` 里的同名说明是同一段，英文文件是它的源头。

所以边界检查几乎不花代价，而**带检查的下标算术**——下标上的 `vela_mul_range` 与 `vela_add_range`——约占剩下那部分的 68%。那就是下一件工作（`selfhost/ELISION_PLAN.md`：证明下标不可能溢出、不再发出这些调用、保持输出完全相同），而这张表就是它值得做的原因。在那之前，"比 C++ 更快"是一个背后有测量的目标，而不是一条断言。

## 可重复性，以及 `parallel for` 确实是真的并行

并行变体才是可能悄悄出错的那一类，所以它们的答案每次运行都会被检查，而下面的线程扫描是在这个编译器上重新取的（2026-09-19）——每个线程数下都有一个校验和：

    OMP_NUM_THREADS=1     0.5338 s    checksum 1090512707
    OMP_NUM_THREADS=2     0.3016 s    checksum 1090512707
    OMP_NUM_THREADS=4     0.1429 s    checksum 1090512707
    OMP_NUM_THREADS=7     0.0914 s    checksum 1090512707
    OMP_NUM_THREADS=16    0.0671 s    checksum 1090512707
    serial reference      0.5455 s    checksum 1090512707

在一台 8 核机器上，从单线程到十六线程是 8.0×，而每个线程数下的答案都一样。那条曲线，加上 `bench\matmul.c` 里的 `#pragma omp parallel for`，就是证据：`parallel for` 编译出的是并行代码，而不是一个配着注释、声称自己并行的串行循环。

上一个冻结里记录的、每个变体跑 25 次的答案检查，以及 `parallel for` 用例跑 90 次的检查，都是在上一代编译器上测的；它们的性质（始终只有一个答案）正是套件自己的 `run` 用例每次运行都会断言的东西，而在这个编译器上重新取那 25 次的计数仍然是有待完成的，而不是被假定的。

## 默认路径自己的数字，而上面每一行都不是关于它的（2026-09-24）

`build` 在 2026-09-24 变成了 LLVM 路径，所以**上面每一个数字都是关于 C 后端**（`build-c`）的，而它已经不是用户默认拿到的东西。harness 用 `build-c` 构建 Vela 那一侧，原因在于这份语料有一半是 `parallel for`，而 LLVM 后端按设计拒绝它——所以那些行根本没法比较——而没有 `parallel for` 的 `bench\matmul_serial.vel`，就是唯一能测**产物路径**的那一行。手工用 LLVM 路径构建，跑五次，同一台机器，同一套协议（程序自己打印它自己的秒数和答案）：

    selfhost\build\vm.exe build <scratch>\mm.vel      # `build` 就是 LLVM 路径
    <scratch>\mm.exe                                  # 跑五次

    0.953164  0.940688  0.966658  0.959652  0.955570      中位数 0.9556 s
    checksum 1090512707 —— 与上面每一行 matmul 打印的值完全相同

| 串行 matmul 512x512，同一个程序，五次的中位数 | 这台机器 |
|---|---|
| C++ 孪生版本（MSVC /O2，无 OpenMP） | 0.2317 s |
| Vela，C 后端（`build-c`） | 0.5554 s —— 是 C++ 孪生的 2.4 倍 |
| **Vela，LLVM 后端（`build`，默认）** | **0.9556 s —— 是 C++ 孪生的 4.1 倍，也是 C 后端的 1.72 倍** |

这就是这个文件本来要回答的那条断言的真实状态：**默认路径才是慢的那一条**，而且它比 C 后端慢的倍数，比 C 后端比 C++ 慢的倍数还大。C 后端的优势来自 MSVC 对发出的 C 的优化——下标算术被内联并被部分消除；而 LLVM 后端每做一次运算就调一次 `vela_llvm_bounds_check`、`vela_llvm_mul_range`、`vela_llvm_add_range`，自己不做任何消除，而（如上面的阶梯表所说）时间恰恰花在那套带检查的算术上。所以 `selfhost\ELISION_PLAN.md` 现在有了比昨天更锋利的目标：决定「比 C++ 更快」这个数字的，是 **LLVM** 发射器产出的那个，而不是 MSVC 从它的 C 里产出的那个。

## 被丢掉的东西

只有一行，而且唯一的理由是它构建不出来：`VELA --fast-int`。这个开关属于已被删除的 Python 前端；这个编译器永远发出带检查的算术，也没有关掉它的开关，所以那一行是被去掉的，而不是被猜出来的。C++ 孪生版本是为这个仓库写的、在同一台机器上、用同一个优化器和同一个算法，而噪声很大的 *worst* 列之所以留在那里，恰恰就是这个原因。
