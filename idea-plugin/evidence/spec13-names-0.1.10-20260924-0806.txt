WHAT THIS FILE IS
=================

0.1.9 taught the plugin to *parse* `enum` and `match`.  This round makes the names the language
gained *usable*: a variant name and an enum's name resolve through the same reference machinery the
plugin already had, find-usages answers at the declaration's own name, parameter info opens for a
variant construction, a payload field is a declaration the hover answers for, and a variant name
has a colour kind of its own.  Every item is measured with a tool that already existed, and every
"before" number is a run of the **same** tool against the **0.1.9 plugin's own classes** and the
**same frozen compiler**, so the plugin build is the only difference.

ITEM 3 -- A VARIANT NAME HAS A COLOUR OF ITS OWN
=================================================

`VelaNameKind.VARIANT`, drawn with the platform's constant colour, for all four positions the
language writes a variant in: the declaration inside the enum body, a construction, an arm's
pattern and a bare value.  The compiler's own dump is the authority that a variant is a variant and
not a plain name -- it prints `variant name=…` for the declaration and `name Circle` at every use.

**NOTHING MEASURES THIS.**  No harness asks which key a name is drawn with; `FeatureProbe` checks
that the keys the *lexer* draws are the keys the colour settings page registers, and these semantic
kinds are drawn with platform defaults and registered nowhere.  The decision is written where it is
made (`VelaSemanticHighlighting`, beside the `colourOf` mapping) and it is stated here rather than
implied to be covered.

ITEM 4 -- A PAYLOAD FIELD IS A DECLARATION
===========================================

What changed: `VelaModel.readEnumFromTree` emits a symbol per payload entry, owned by the variant
that carries it, so the hover for `radius` is the declaration the compiler's dump prints
(`field radius: float`, owner `Circle`).  `HoverTruth` judges those positions now instead of
counting them.

    0.1.9 jar   COVERAGE: ran 13013 / skipped 96 (... payload-field-not-a-model-declaration 15 ...) / wrong 0
    0.1.10 jar  COVERAGE: ran 13028 / skipped 81 (...) / wrong 0

The 15 positions moved out of the counted class into `ran`, and `skipped` fell by exactly 15.

**It went red first, and the red was this round's own harness bug** -- the dump reader set the
payload's owner where it recognised the line, and then the reader's common tail overwrote it:

    e.nested = nestedInDef(parent);
    if (e.kind.equals("field")) e.owner = e.nested ? "" : structOf(parent);   // "" for a payload

`structOf(parent)` walks up looking for a `struct`, and a payload's parent is a **variant**.  The
plugin was right and the tool was wrong:

WHAT THIS PLUGIN STILL CANNOT DO FOR §13, NAMED WITH ITS COST
=============================================================

  * **A pattern binding's name is not resolved.**  `Circle(r)` binds `r` positionally; the arm's
    body uses `r`, and `VelaTargets.declarationFor` has no case for a binding declared by an arm.
    Those uses are `GotoOracle`'s `invisible-member` class (3 of them on
    `enum_exhaustive_switch.vel`, 18 over the corpus, each printed with its line), and no rename can
    reach them.
  * **A payload field's name is not resolvable** -- and cannot be: nothing in the language writes
    one.  Its declaration is hoverable (item 4), and no use of it exists to go to.
  * **The semantic colour of a variant name is measured by nothing** (item 3).
  * The plugin's parser still reproduces only the compiler's *parse* refusals, not its *checker*
    refusals; a file the checker refuses is a tree here and a diagnostic from `vm.exe check` in the
    editor.

PROCESS FINDINGS, BECAUSE THEY COST THIS ROUND SOMETHING
========================================================

  * **The 0.1.9 dist zip was overwritten**, and with it the plugin classes every before/after above
    is measured against.  `build-offline.ps1` names the zip after `<version>` in `plugin.xml`; this
    round's version stayed 0.1.9 until its last step, and three intermediate builds wrote
    `dist\vela-idea-plugin-0.1.9.zip` from work in progress.  What saved the round is
    `harness.ps1`'s own design: it snapshots `build\classes` to
    `build\tools\harness\classes\classes-snapshot-<pid>` before every run, so a concurrent build
    cannot disturb it, and `classes-snapshot-41940` is the 0.1.9 build.  The discipline is now
    observed in the other order: **bump the version first, then build**.
  * **One differential ran against the wrong compiler**: `ast-diff.ps1` was invoked without
    `-FrozenVm`, so it froze the tree's own `vm.exe` -- which the other track was rebuilding at that
    moment -- and reported every `enum_*` file as "compiler refused ... but this parser accepted
    it".  Re-run against the pinned copy it is the PASS quoted above.  The failing run is worth
    keeping because the red looked exactly like a plugin defect and was a property of the binary.
  * **A harness instrument, in the same family**: one of this round's edits to `HoverTruth.java`
    was lost to a concurrent write to the same file and the tool then failed to compile at all --
    which, under `harness.ps1`'s one-javac-call design, makes *all fifteen* tools fail with a
    message about the one file.  It was caught by running the tool immediately after editing.
