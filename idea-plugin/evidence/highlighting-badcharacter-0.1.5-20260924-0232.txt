WHAT WAS ASKED
    The task said FeatureProbe section 1 reported a user-visible defect: the lexer emits
    BAD_CHARACTER and the plugin declares no colour key for it, so a character Vela does
    not know would be drawn blank.  The acceptance test was "token types with no colour: 0"
    plus a deleted-mapping control that must go red again.

WHAT IS TRUE
    The plugin was already correct.  `VelaHighlighting.kt` declares
    `VelaColors.BAD = TextAttributesKey.createTextAttributesKey("VELA_BAD",
    HighlighterColors.BAD_CHARACTER)` and maps the token
    (`TokenType.BAD_CHARACTER -> arrayOf(VelaColors.BAD)`); `VelaColorSettingsPage.kt`
    line 61 already shows it as "Bad character".  The red row came from the probe:

      FeatureProbe.elementTypeNamed(name) filtered a hard-coded list of the 13
      VelaTokenTypes constants.  An unknown character is returned by
      VelaLexer.scanOperator as TokenType.BAD_CHARACTER -- the *platform's* type, which
      is not one of those 13 -- so the lookup returned null, the token was recorded as
      "no IElementType with that name", and getTokenHighlights() was NEVER CALLED.
      Section 1 therefore could not go green no matter what the plugin did, and could
      not go red either when the mapping was deleted: it was unfalsifiable for exactly
      one token kind, and it reported a verdict about a call it never made.

    Independent, source-level check of the plugin itself (throwaway probe in %TEMP%,
    no repo file involved):

      lexer token type for '@' : BAD_CHARACTER  class=com.intellij.psi.tree.IElementType
                                 identity=TokenType.BAD_CHARACTER
      getTokenHighlights(BAD_CHARACTER).length = 1
         key      : VELA_BAD  sameObjectAsVelaColors.BAD=true
      VelaColors.BAD external name = VELA_BAD

THE FIX (approved by the leader; outside this agent's original whitelist on purpose)
    idea-plugin\tools\harness\src\FeatureProbe.java, elementTypeNamed, one lookup:

        if (TokenType.BAD_CHARACTER.toString().equals(name)) return TokenType.BAD_CHARACTER;

    No plugin source file was changed by this work.  VelaColors.BAD was deliberately
    NOT given a hard-coded red foreground: it inherits the user's "Bad character" colour
    from their scheme, and a hard-coded value would override the settings row this
    plugin ships -- making a hard-coded colour win over a user's choice, which is worse
    than the state being reported.

WHAT THE PATCHED PROBE STILL DOES NOT MEASURE  (control D, and it must be said plainly)
================================================================================
Section 1 asks one question: does `getTokenHighlights(t)` return at least one key for
every token type the lexer emits over the corpus?  It does NOT ask whether that key is
the one the colour settings page registers, and it cannot: a TextAttributesKey is
looked up by object identity in a scheme, so the highlighter keeps working even if its
key is renamed.

Measured (run D): renaming the key's external name to "VELA_BAD_TYPO" in
VelaHighlighting.kt -- while VelaColorSettingsPage.kt still lists `VelaColors.BAD` --
still reads "BAD_CHARACTER 5 coloured" and section 1 still PASSES.  That tree has a
settings row whose name is no longer the name of the key the editor resolves, so the
row is a setting a user can change and that changes nothing.  Section 1 cannot see it.

A criterion that CAN fail on that defect, executable today with the classes already on
the harness classpath -- compare *names*, and only then ask about the keys:

    VelaSyntaxHighlighter h = new VelaSyntaxHighlighter();
    Set<String> drawn = new TreeSet<>();
    for (IElementType t : /* every type the lexer emits over the corpus, by name */)
        for (TextAttributesKey k : h.getTokenHighlights(t)) drawn.add(k.getExternalName());

    Set<String> listed = new TreeSet<>();
    for (AttributesDescriptor d : new VelaColorsAndFontsPage().getAttributeDescriptors())
        listed.add(d.getKey().getExternalName());

    require drawn.equals(listed);          // else: a row that changes nothing, or a key with no row

Run D fails `drawn.equals(listed)` ("VELA_BAD_TYPO" vs "VELA_BAD") and every other run
here passes it, so that is the assertion worth adding if this must be caught rather
than described.  One more dimension neither the existing section nor that one covers:
the resolved *effective* attributes.  A key can be mapped and still resolve to nothing
(no foreground in the scheme and no fallback), and only
`EditorColorsManager.getGlobalScheme().getAttributes(key).getForegroundColor() != null`
says whether the character is actually visible -- it needs an Application instance,
which the harnesses in this plugin deliberately do not start.

WHAT WENT WRONG IN THE FIRST REPORT THIS WORK RECEIVED
================================================================================
"the plugin declares no colour key for BAD_CHARACTER, so the character is drawn blank"
was false, and the tree it was read from was not defect-free either: the tool's own
verdict was the only evidence, and the tool had not called the function it judged.
Section 1 named the defect as "no IElementType with that name" -- i.e. it said out loud
that it could not resolve the type, and still printed a verdict about the highlighter.
That parenthetical is the piece of evidence that was in the output all along.
