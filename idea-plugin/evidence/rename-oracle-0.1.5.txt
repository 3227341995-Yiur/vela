================================================================================
WHAT THE ORACLE IS, IN ONE PARAGRAPH
================================================================================

"Which occurrences are uses of declaration D, and which characters must a rename of D
write?" has one authority: the compiler.  `vm.exe check` prints a line number and never a
column, so the protocol uses the compiler as a *difference* oracle rather than reading its
messages: rename D's declaration alone and run `check`; rename the first remaining
occurrence of the name on each line the compiler names and run again, until the file
compiles (that verified line set bounds the candidates); then rename D and every candidate
and require the file to compile (the basis guard); then, one candidate at a time, rename D
and every candidate EXCEPT that one -- the file is refused exactly when the compiler binds
the old name there to D.  That last step is what makes the binding set offset-by-offset
rather than line-by-line, and it is a measurement rather than an inference: with the basis
compiling, renaming candidates introduces no error of its own, so a refusal can only be an
occurrence that had to be renamed.

Three verdict classes, and only two of them are decided by the compiler:

  MISSED        the compiler requires the occurrence, the reference table has nothing
                there.  A defect: the rename built from that table leaves it behind.
  WRONG-SCOPE   the table claims the occurrence for D and the compiler binds it to a
                *different* declaration of the same name.  A defect, and the one the tool
                exists for -- another scope's same-named variable being renamed.
  NOT-REQUIRED  the table claims it, D does not require it, no other declaration does
                either.  UNPROVABLE, counted and printed, never called wrong: the
                compiler does not resolve that position at all, or cannot see the
                difference.  Measured example, `tests/build/struct_value_semantics.vel`:
                `mut a: P = P(1)` -- both the annotation and the constructor must be
                renamed or `check` refuses the file; `b: P = a` -- the same annotation on
                an immutable binding is not resolved, and renaming the struct while
                leaving that `P` behind still exits 0.  This is GotoOracle's "the
                compiler's silence is not a denial", the same fact about the same binary.

The plugin's answer is `VelaReferences.referenceTargetAt(text, leafStart, leafEnd)`, asked
once per `IDENTIFIER` leaf -- the exact candidate set `VelaReferenceContributor` registers
the provider over and the words scanner indexes, and the same call the provider makes.
`claimed(D)` is the set of leaves that answer D, and the rename the platform performs is
the declaration element plus `claimed(D)`.

--- 2b. A method call on a nested receiver had no reference (real, fixed) -------

  tests/safety/cases/hole_parallel_impure_method_nested_receiver.vel:10 `bump` (method)

4. THE MEASURED DEFECT THIS TRACK CANNOT FIX (handed over, not hidden)
================================================================================

`tests/safety/cases/scope_shadow_across_blocks_ok.vel`:

  5  x: int = 1          <- outer binding
  6  if x == 1 {
  7      x: int = 2      <- inner binding, a DIFFERENT declaration
  8      print(x)
  9  }
 10  print(x)

`vm.exe parse` for this file (the tree `ast-diff.ps1` holds the plugin's parser to) puts the
inner `decl` inside the nested block, so the two declarations are distinct nodes.

The reference table credits `print(x)` on line 8 to the OUTER `x` (offset 292 is in the
outer's claimed set and in no measured binding set), so a rename of the outer `x` rewrites
the inner block's use.  The cause is `VelaTargets.declarationFor` case 3: it walks the
ancestor chain from the OUTSIDE IN and returns at the first block that holds a matching
declaration, so the outer binding wins over the inner one -- against its own header comment
("a local binding that precedes this use, innermost block first ... so an inner binding
shadows an outer one") and against the language's shadowing rule (`SPEC.md` 6.2, the file's
own comment).

The tool cannot call this wrong, and says so rather than guessing: renaming EITHER
declaration leaves the program compiling (with the inner declaration renamed, `x` on line 8
resolves to the outer one; with the outer renamed, the inner block is untouched), so
`vm.exe check` cannot see the difference.  It is therefore the NOT-REQUIRED row of section 1.
What made the *other* half of the same defect visible was this track's own fix: before it,
the inner declaration's own name (offset 267) was ALSO credited to the outer `x`, and a
declaration's own name is not a reference by the plugin's own token-shape rule -- so
`declarationTarget` now answers null there.  The remaining half needs a change in
`VelaTargets.kt` (walk the chain innermost-first, one line of ordering), which is outside
this track's file list and changes what `GotoOracle` measures, so it is reported instead:
the row-10 owner should re-run `GotoOracle` after it.

A next step that WOULD decide it, recorded here as a proposal and not as a claim: `vm.exe
run` on a program whose two same-named bindings hold different values, comparing the output
before and after the plugin's rename.  A rename that changes a program's output is wrong
whatever the type checker thinks.  It is not implemented because running the corpus means
running `tests/run_tests.vel` and `bench/*`, which shell out and take minutes, and a
behavioural oracle needs per-file judgement about whether a file is runnable at all.

  the pure functions behind them (`VelaUsageSearch.canSearchAt` / `typeAt`, one line each in
  `VelaFindUsagesProvider`), not by opening a Find Usages window; the same limit applies to
  every other feature in this plugin and is stated the same way.
* The write-back itself is measured as the character ranges the platform replaces
  (`claimed(D)` plus the declaration, applied as `document.replaceString` does), not by
  driving `VelaLeafManipulator` through a live document: a `PsiElement` needs an editor.
  `VelaReferences.isWritableName` -- the pure half of `canWrite` -- is the part that IS
  measured, because the oracle refuses to run on a name the write-back would refuse.
* Undo granularity, the rename dialog, conflict validation and rename of a name in a string
  or a comment are not measured.
* The corpus is the worktree's current state, including files other tracks are editing.  The
  oracle cache is keyed by (compiler sha256, file hash, declaration), so an edited file is
  re-measured rather than reused; a file's *hash* is what makes that true, and it is why the
  cache can be shared between the shipped and the mutated classpath (the oracle's answers
  are properties of the compiler and the file, not of the plugin).
* `selfhost/vm.vel` (631 KB) is not in the corpus, for the reason GotoOracle gives.
* The tool is not yet in `harness.ps1`'s `$TOOLS` list -- that file belongs to another track.
  The two-line change it needs:

      $TOOLS = @('GotoOracle', 'HintDiff', 'HintNames', 'HintShapes', 'HintDupes', 'SymbolDiff',
                 'FoldDiff', 'FeatureProbe', 'ParamNames', 'HintTruth', 'RenameOracle')

      'RenameOracle' {
          $a += @('--vm', $FrozenVm, '--cache', $oracleCache)
          if ($RebuildOracle) { $a += '--rebuild-oracle' }
          if ($Single)        { $a += @('--single', $Single) }
      }

  (a separate cache file is better: `rename-oracle.txt`, so the two oracles cannot invalidate
  each other's entries -- they are keyed by the same compiler and file hashes but store
  different shapes.)
* NO `plugin.xml` change is needed.  Find Usages and rename are already registered
  (`<lang.findUsagesProvider language="Vela">`, `<psi.referenceContributor>`,
  `<lang.elementManipulator forClass="com.intellij.psi.PsiElement">`); this track changed no
  registration, added no extension point, and touched no version number.
* `tools\harness\src` was verified to compile as a whole directory (all 20 sources,
  including the other tracks' `HoverTruth.java` and `InspectionProbe.java`) against this
  track's classes before this file was written: exit 0, 3 deprecation warnings.  The
  whole-directory compile is what `harness.ps1` does on every run, so a tool that does not
  compile there stops all ten other tools -- this one does compile, and it is `RenameOracle`
  alone that the driver compiles by default so that a half-finished neighbour cannot break
  this track's runs.
