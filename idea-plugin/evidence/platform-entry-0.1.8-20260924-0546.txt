WHAT THE FIX IS
===============

  * `VelaTargets.localBindingType(text, at, name)` -- new.  Reads the parser tree's own `decl` node
    for the nearest binding of that name **above** `at` inside the enclosing blocks, **inner block
    first** (the compiler's shadowing rule, SPEC.md 6.2, which `VelaTargets.declarationFor` case 3
    already follows for uses).  Three answers, and the caller distinguishes them: the type written
    beside the name; the empty string for a binding that writes no type (the compiler refuses such
    a file -- `binding 'n' has no type annotation` -- so this is a file being typed, and a local
    still shadows, so the honest answer is "the file does not say" and never the outer name's
    type); and null for no binding at all, which is what lets the parameter and struct-name
    readings run.
  * `VelaNames.structTypeOf` asks it **first**, before the parameter loop, because that is what
    shadowing means.  Its doc comment used to say Vela "has no local type annotations", which was
    simply false; it names the four receivers now.
  * **The remaining counted position is named, not hidden.**  `tests/safety/cases/
    hole_parallel_impure_method_nested_receiver.vel:25` is `inner.` where `inner` is a *field* of
    the enclosing struct: the compiler's dump types it (`field (Inner) + attr`), and no binding
    writes that type beside a name, so the plugin answers nothing there **by design**.  It is
    `receiver-not-a-written-binding` (1 position, and 0 in row 9), and the skip row prints the
    declaration's own node kinds rather than the harness's guess at them.

WHAT THE FIX IS
===============

`VelaParameterInfoHandler.findElementForUpdatingParameterInfo` used to read the items back as:

    (shown[0] as? PsiElement)?.let { if (it.getUserData(HINT) != null) return it }

Those items are `ParameterHint`s -- `showParameterInfo` puts the hint itself in `itemsToShow` -- so
the cast could not succeed and the branch was a fossil that looked like a safety net.  The handler
now looks for the item among `objectsToView`, checks that the offset still holds the call's own `(`
(after an edit that moved the text the honest answer is to let the popup close, not to hang the
hint on whatever token the old offset now lands in), puts the hint back on the leaf it finds, and
answers null when there is nothing shown.  The harness measures all of that, including the
falsification: with `objectsToView` empty the handler must answer *null*, and before the positive
check runs the tool requires that same null answer, so a rebuilt leaf that still carried the hint
would be reported as `rebuilt-anchor-unavailable` 663 times rather than passing the check
vacuously.

Row 19 is untouched by either fix, and it is in both runs: `ran 8329 / skipped 1107 (...) / wrong 0`
on the 0.1.7 jar and on this one, which is why the combined line moves by exactly the 28 and 663
above and nothing else.
