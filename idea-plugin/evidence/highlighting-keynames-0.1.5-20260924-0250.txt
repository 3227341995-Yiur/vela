READ THIS FIRST: harness.ps1 DOES NOT RECOMPILE KOTLIN.

  Every .kt edit in this file is compiled by build-offline.ps1 -SkipVerify BEFORE the
  harness runs. skipping that, and running harness.ps1 alone against a tree whose
  Kotlin was just edited, measures build\classes as it was left by whoever built last.
  Measured in round 1 of this work: after deleting the BAD_CHARACTER mapping from
  VelaHighlighting.kt, the harness still reported "BAD_CHARACTER 5 coloured", because
  build\classes\dev\vela\plugin\VelaSyntaxHighlighter.class still had its 02:14:49
  mtime.  A red/green result that did not rebuild is not a result about the source.
  In this round every variant is a full private kotlinc build of the whole plugin,
  and the probe prints the code source of the page it loaded, so "which copy answered"
  is checked rather than assumed.

WHAT ROUND 2 ADDS

  Round 1 established that section 1 never called the highlighter for the platform
  token type and therefore could not fail for BAD_CHARACTER.  It now can.  That left
  the shallower question: section 1 asked only whether getTokenHighlights(t) returned
  AT LEAST ONE key.  A TextAttributesKey is looked up by identity in a colour scheme,
  so a key whose external NAME drifted from the name the colour settings page
  registers still colours the token while its settings row becomes a row that changes
  nothing -- and section 1 could not see it.  Section 1 now has three parts:

    1a  every token type the lexer emits has at least one colour key   (round 1)
    1b  the keys drawn and the keys the settings page registers carry the SAME names
    1c  a key resolves to an actual colour in the user scheme -- declared as a named
        skip (needs-an-application-instance) because it needs a running Application

WHY 1b IS A SUB-CHECK OF SECTION 1 AND NOT A NEW SECTION

  Sections 2-6 are per-corpus-file, and the coverage unit -- "one (capability, file)
  pair for sections 1-5, plus one artifact-level check for section 6" -- is stated in
  the tool.  A seventh section would make that sentence and the "[FAIL] n of 6" wording
  wrong for a check that is about two classes, not about the corpus.  1b compares two
  sets once, prints both, and reports under section 1, where a reader already looks for
  "is highlighting wired up".  Its failures go into the same `wrong` count and the same
  sectionFailures list, so the aggregate verdict cannot be greener than it.

C. 1c: THE CHECK THAT IS DECLARED AND NOT RUN
================================================================================

  Resolving a key in the user's scheme needs EditorColorsManager.getInstance(), i.e. a
  running Application.  This plugin's harnesses deliberately start none, so 1c cannot
  run here -- and the coverage line says so by name instead of saying nothing:

    COVERAGE: ran 1556 / skipped 1 (missing-corpus-file 0, too-large 0,
              empty-or-whitespace-only 0, needs-an-application-instance 1) / wrong 0

  The category is declared up front, so a reader sees "1" rather than having to guess
  whether the check was counted.  What it would check: a key that is mapped and
  registered can still resolve to nothing (no foreground, no fallback), and then the
  character is on screen and invisible -- the user-visible symptom this whole section
  exists to rule out.  The exception text is printed verbatim in the run output above
  (NullPointerException from ApplicationManager.getApplication() == null).
