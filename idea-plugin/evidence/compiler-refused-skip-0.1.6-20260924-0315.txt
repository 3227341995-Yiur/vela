# 9. WHAT THE CLASS DOES NOT COVER (limits, stated rather than implied)
##############################################################################
  * a file the compiler cannot PARSE keeps its own existing class (compiler-cannot-parse):
    HintDiff reports it separately, so 'the parser could not read it' and 'the language does
    not have this program' never look the same.
  * a refused file with NO finding is judged rather than skipped -- its units stay on the
    ran side, which is a stronger statement than not looking at it.
  * if check does not answer within 30 s the file's findings STAND and the run carries a
    named check-timed-out defect (exit 3): the one authority could not be asked.
  * nothing here changes the exit code for a skipped file: the skip side has no vote.
  * the harness's -Single switch is not passed to HintNames (the tool takes no --single, and
    an unknown flag used to become the repo root -- see control B).

The section 8 line "'MUTANT' occurrences in the tree's harness sources: 0" was computed over
tools\harness\src\*.java, which is non-recursive.  At the time it was written the tree also
held a stray tools\harness\src\mutant\ directory: an earlier attempt at the control used a
PowerShell variable named $src, which is the SAME variable as $SRC in that shell (case is not
significant there), so the mutant copies were written under the harness source directory
instead of %TEMP%.  That attempt never compiled (its classpath variable had been clobbered
too), and every mutant run reported in section 5 was built and run from %TEMP%, from the
corrected script.  The stray directory has been deleted; the tree now holds no mutant copy and
no control remnant, and the two tool sources are byte-identical to the snapshot taken before
any control ran (section 8).
