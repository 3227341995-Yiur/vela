1. REPRODUCING IT FIRST: WHERE THE DEFECT IS, AND WHY
================================================================================

`tests/safety/cases/scope_shadow_across_blocks_ok.vel` is 9 code lines:

   4  def main() -> None {
   5      x: int = 1
   6      if x == 1 {
   7          x: int = 2
   8          print(x)
   9      }
  10      print(x)
  11  }

The outer `x` (line 5) and the inner `x` (line 7) are two declarations in two scopes.  The
language's rule is SPEC.md line 352: "Shadowing across blocks stays legal; it is a
*redeclaration in one scope* that is refused".  So the `print(x)` on line 8 -- written inside
the inner block -- is a use of the INNER `x`, and line 10 is a use of the OUTER one.

`VelaTargets.declarationFor` (VelaTargets.kt:176) resolves a name by walking the chain of
nodes containing it.  That chain is built by `chainAt`, whose own doc comment (line 356) says
"The chain of nodes containing [at], outermost first, innermost last", and it is built that way
(line 360 pushes `tree.root` first, then appends each containing child).  Case 3 -- the
block-binding case -- carried a header comment (line 210) reading "A local binding that
precedes this use, innermost block first", and under it:

    for (node in chain) {                                    // VelaTargets.kt:211
        if (node.kind != VelaNodeKind.BLOCK &&
            node.kind != VelaNodeKind.MODULE_BLOCK) continue
        ...                                                  // best = last matching DECL in this block
        if (best != null) return targetAt(tree, best!!, VelaTargetKind.LOCAL)   // line 224
    }

Walking an outermost-first list from the FRONT visits the OUTERMOST block first, and line 224
RETURNS at the first block that holds a matching declaration.  For the `print(x)` on line 8 the
chain is root -> MODULE_BLOCK -> DEF(main) -> BLOCK(main body) -> IF -> BLOCK(inner), so the
walk reaches BLOCK(main body) first, finds the `x` declared on line 5 in it, and returns.  The
inner `x` on line 7 is never consulted.  (Case 2, the `for` loop above it, also walks forward
but is NOT affected: `parseFor` stores the loop variable on the FOR node itself
(`n.name = varName`, VelaSyntax.kt:1658), so the innermost `for` is already the first `FOR` a
forward walk meets.)

So the defect is line 211's loop direction against line 356's documented chain order and the
language rule.  Its consequence is not a matter of argument: the OUTER declaration's reference
set gains a use that belongs to the inner declaration, so renaming the outer `x` rewrites the
inner block's `print(x)`, and renaming the inner `x` leaves that use behind -- while
`vm.exe check` sees neither, because both bindings are `int` and renaming either declaration
leaves the program compiling.  That is precisely why the prior track handed this over instead
of fixing it: RenameOracle cannot call it WRONG, and says so rather than guessing.
